# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (main.py) | The code decides "is this late?" using minutes that were already rounded down to a whole number, instead of the exact time difference. So a punch-in that's just a second or two past the 10-minute grace period gets treated as on-time instead of late as is given in the example of R2 of Problem statement doc. | Shift starts at 09:30. Punch in at 09:40:01 (one second past the grace period) — the rule says this should count as 10 minutes late, but the old code returns 0. | Compare the exact number of seconds late against 600 (10 minutes) first, and only round down to whole minutes afterwards for the value that gets returned. |
| 2 | `compute_work_hours` (main.py) | Python's built-in `round()` rounds ".5" values to the nearest *even* number, not always up. The spec wants normal "round half up" behaviour. | Any work-hours value that lands exactly on a rounding boundary (e.g. something that should round to 9.125 -> 9.13) can come out rounded down instead of up, depending on the digit before it. | Switched to `Decimal` with `ROUND_HALF_UP`, which always rounds .5 upward, matching the spec. |
| 3 | `compute_overtime` (main.py) | Two problems in one function: (a) it never checks the "at least 30 minutes" rule, so even 1 minute of overtime was being reported; (b) it built one time as "aware" (tagged with the IST timezone) and compared it to `punch_out`, which is a plain untagged time — Python refuses to compare those and crashes. | (a) Punch out 5 minutes after shift end — old code returns `5`, should return `0`. (b) Calling this function at all with a real `punch_out` throws `TypeError: can't subtract offset-naive and offset-aware datetimes`. | Removed the IST tag so both times being compared are the same "plain" kind, and added a check that returns 0 unless the overtime is 30 minutes or more. |
| 4 | `EmployeeIn` model | The model accepted literally any string for every field — no checks on the employee code format, email shape, text length limits, or that `joined_on` is a real calendar date. It also never checked that `shift_start` and `shift_end` are different, even though the contract requires that. | POST an employee with `emp_code: "hello"`, `email: "not-an-email"`, or `joined_on: "2026-13-45"` -- all of this is currently accepted and stored instead of being rejected with a 422. | Added the same format rules as the contract: `emp_code` must look like `EMP0001`, email must have an `@` and a domain, name/department have sane length limits, shift times must be `HH:MM`, and two small checks confirm `joined_on` is a real date and that the two shift times differ. |
| 5 | `PunchInIn` model | `status` accepted any string at all, so a client could punch in with `status: "LEAVE"` even though the contract says no endpoint is allowed to create LEAVE records. `punched_at` accepted any integer with no range check, so a timestamp in seconds (instead of milliseconds) or an out-of-range number would silently be treated as valid. | POST `/attendance/punch-in` with `status: "LEAVE"` is currently accepted. Sending `punched_at: 1783312500` (seconds, not milliseconds) is also accepted, even though the contract says it must be rejected. | Restricted `status` to only `PRESENT`, `WFH`, `ON_DUTY`, and added strict min/max bounds on `punched_at` so anything that isn't a real millisecond timestamp in a sane range is rejected with a 422. |
| 6 | `health()` | The health check always returned "ok' without ever asking MongoDB anything. If the database was down, this endpoint would still say everything is fine. | Stop the Mongo container and call `GET /health` -- it still returns 200 `ok`, but every other endpoint would be failing. | Added a real ping (`client.admin.command("ping")`); if the ping call fails for any reason, the endpoint now returns 503 instead of lying. |
| 7 | `create_employee()` | Checked for emp_code deduplication and only inserted afterwards. Two requests arriving at the same instant can both pass the check before either one inserts, so both get created with the same `emp_code` — the exact race the contract calls out. There was also no unique index in the database to stop this at the data layer. | Fire two `POST /employees` requests at the same time with the same `emp_code` — both can return 201, and the database ends up with two documents sharing one `emp_code`. | Added a unique index on `emp_code` at startup, removed the "check first" step, and now just try to insert directly; MongoDB itself rejects the second insert, which we catch and turn into a 409. |
| 8 | `create_employee()` | `created_at` was set with `datetime.now()`, which is the server's local wall-clock time with no timezone attached, instead of UTC like the data model expects. | If the server running the app isn't set to UTC, every employee's `created_at` is simply wrong and we could get inconsistent timestamps. | Changed to `datetime.now(timezone.utc)`, an explicit UTC timestamp. |
| 9 | `create_employee()`, `list_employees()` | `created_at` was returned straight from MongoDB as a raw date/time value. The contract says every instant in a response must be a plain integer (milliseconds since 1970), not a date object. | Create an employee and look at the response body. `created_at` comes back as a timestamp string, not the integer the contract and the API docs expect. | Added a small helper that turns a stored date into the required integer, and used it everywhere an employee is returned. |
| 10 | `list_employees()` | Pagination math was `skip = page * page_size`, which skips an extra page's worth of results every time. Page 1 was skipping the first page instead of returning it. | logical bug | Fixed to the standard `skip = (page - 1) * page_size`. |
| 11 | `list_employees()` | `total` always counted every employee in the whole collection, even when a `department` filter was applied, so a filtered search would show the right employees but the wrong total count. | Filter by a department with only 2 employees in it — `items` correctly shows 2, but `total` shows the full headcount of the company instead of 2. | `total` now counts the same filtered query (`q`) that's used to fetch the results, instead of counting everything. |
| 12 | `list_employees()` | No sort was applied at all, so the order employees come back in is whatever MongoDB happens to return, which isn't guaranteed to be consistent. The contract requires results sorted by `emp_code` ascending. | Call the endpoint twice in a row on an unchanged dataset — nothing guarantees the order stays the same, and it won't match `emp_code` order. | Added `.sort("emp_code", 1)`. |
| 13 | `list_employees()` | `page` and `page_size` had no limits, so a caller could send `page_size=100000` or a negative `page` and get unpredictable behaviour instead of a clean validation error. | `GET /employees?page_size=99999` is accepted as-is today, even though the contract caps `page_size` at 100. | Used FastAPI's `Query` with `ge=1` on `page` and `ge=1, le=100` on `page_size`, so out-of-range values now correctly fail with 422. |
| 14 | `punch_in()` | If `emp_code` doesn't exist, `db.employees.find_one` returns `None`, and the very next line reads `emp["shift_start"]` off that `None` — the request crashes instead of giving a clean error. | POST `/attendance/punch-in` with an `emp_code` that was never created — the old code throws an unhandled `TypeError` (500) instead of a 404. | Added a check right after the lookup: if no employee was found, return 404 before touching `emp` again. |
| 15 | `punch_in()` | The punch time was converted with `datetime.fromtimestamp(ms/1000)`, which uses *the server's own local clock setting*, not a fixed timezone. Every date/late/overtime calculation downstream depends on this being correct IST time. | If the machine running the app isn't set to IST (very likely on a plain Linux/container host, which usually defaults to UTC), every attendance date and late-minutes value would silently come out wrong. | Added a helper that converts the epoch-ms value to an explicit UTC datetime, then converts *that* to IST wherever wall-clock time is needed — never relying on the server's own timezone setting. |
| 16 | `punch_in()` | The attendance `date` was always set to the punch-in's own calendar date. The spec has an exception for overnight shifts (e.g. 22:00-06:00): a punch-in that happens just after midnight, before the shift's end time, actually belongs to the *previous* day's shift. | An overnight-shift employee punches in at 00:30 (just after midnight) — the old code would file this under today's date, but it should be filed under yesterday's shift. | Added a helper that checks for this overnight case and shifts the date back by one day when it applies. |
| 17 | `punch_in()` | Same race-condition pattern as employee creation: it checked "is there already a record for this employee and date?" and only inserted afterwards, with no unique index backing the check. Two simultaneous punch-ins for the same employee/date could both succeed. | Fire two `POST /attendance/punch-in` requests at the same instant for the same employee — both could return 201 with two records for the same day. | Added a unique index on `(emp_code, date)` at startup, removed the "check first" step, and now insert directly, catching the resulting `DuplicateKeyError` and turning it into a 409. |
| 18 | `punch_in()`, `list_attendance()` | The response for an attendance record added a stray `id` field (attendance records don't have one — they're identified by emp_code + date) and returned `punch_in`/`punch_out` as raw date values instead of the required epoch-millisecond integers (or `null`). Nested dates inside a record's `history` entries had the same problem. | Call either endpoint and look at the response — `id` shouldn't be there at all, and `punch_in` comes back as a timestamp string instead of a plain integer. | Added a shared helper that builds the response for any attendance record: it drops `id`/`_id`, converts `punch_in`/`punch_out` to epoch-ms (or `null`), and converts the dates inside `history` the same way. Used it in both endpoints so the shape is identical everywhere. |
| 19 | `list_attendance()` | Loaded every attendance record matching the filters into a Python list, sorted it in Python, and only then sliced out the requested page. The spec requires this to stay fast on a collection of about 100,000 records and explicitly says not to load the collection into memory. | With a large dataset, asking for a late page (e.g. page 50) still pulls every matching record across the network and into memory first, just to throw most of it away. | Moved the sort, skip, and limit into the MongoDB query itself (`.sort(...).skip(...).limit(...)`), so MongoDB only ever sends back the one page that's actually needed. |
| 20 | `list_attendance()` | The sort was by `date` only. The spec requires a tiebreaker: `date` descending, then `emp_code` ascending for records on the same day. | Two records on the same date come back in an unpredictable order relative to each other. | Added `emp_code` ascending as a second sort key. |
| 21 | `list_attendance()` | There was no check that `date_from` isn't after `date_to`. The spec says this combination should be rejected with 422. | `GET /attendance?date_from=2026-07-20&date_to=2026-07-01` is accepted today and just silently returns an empty result instead of failing validation. | Added an explicit check that returns 422 when `date_from > date_to`. |
| 22 | `list_attendance()` | The `status` query parameter accepted any string at all, including values that aren't real statuses. | `GET /attendance?status=NOT_A_REAL_STATUS` is accepted today and just returns zero results instead of a validation error. | Restricted `status` to the five real status values, so an invalid one now fails with 422. |
| 23 | `list_attendance()` | Same as `list_employees()`: `page` and `page_size` had no limits. | `GET /attendance?page_size=99999` is accepted as-is today. | Added the same `Query(ge=..., le=...)` bounds used in `list_employees()`. |

Also note anything you looked at and decided was **not** a defect, and why.

- `list_employees()`'s `department` filter does an exact, case-sensitive match on the stored value with no extra normalisation (lowercasing, trimming, etc.). The contract explicitly says department matching is "exact, case-sensitive," so this is correct as written, not a bug.
- `compute_overtime()`'s handling of an overnight shift's end date (the shift end actually falls on the day after the record's date) is not yet fixed — this function isn't called by any endpoint in the starter yet (it's wired up for `punch-out`, which doesn't exist until Part B), so it's being addressed when that endpoint is built rather than in isolation here.
